# 长任务委派模板：让交付物落在磁盘上，而不是攒在最后一条回复里

## 为什么需要它

`harvestOrphanedSubagents` 能在子代理随进程死掉之后，把它**已经产出的过程**捞回来。
但它救不回**从未生成的东西**——子代理死在写报告之前，那份报告在任何地方都不存在。

真实案例（本机 transcript 实录）：一个子代理的最后一句是

```
I have everything I need from the files I already read. Writing the full report now.
```

它正好死在出报告的前一步。抢救能告诉你它读完了、准备好了，但报告本身是零。

**根因不是进程模型，是交付方式**：把十几分钟的成果攒到最后一条回复里，就等于赌这条
回复能活到最后。会话一断、进程一挂，赌注全没。

**解法**：让子代理**边跑边把结果写进文件**。交付物落在磁盘上，跟会话生死彻底解耦。
断了重连，写了 70% 就是 70%，不是 0。

## 模板

委派长任务时，把下面这段放进给子代理的 prompt：

```text
【交付方式（必须遵守）】
你的交付物是文件，不是这次对话的最终回复。

1. 动手前先创建 `<报告路径>`，写入标题和一个章节清单（占位即可）。
2. 每完成一个章节，立刻把它追加写入该文件——不要攒着最后一次性写。
3. 每次写入后，文件都必须是一份「到目前为止完整可读」的文档。
4. 全部完成后，最终回复只要一句话：报告路径 + 一行结论。

原因：你可能在跑完之前被中断。已经写进文件的内容才算数，
只存在于你上下文里的内容会全部丢失。
```

把 `<报告路径>` 换成具体路径，例如 `reports/竞品分析-01.md`。

## 并行多个 agent 时

每个 agent 一个**独立文件**，避免并发写同一个文件互相覆盖：

```text
agent 1 → reports/01-<主题>.md
agent 2 → reports/02-<主题>.md
agent 3 → reports/03-<主题>.md
```

主会话最后只负责读这几个文件做汇总——汇总这一步很短，即使断了重跑代价也极小。

## 什么时候该用

| 场景 | 用不用 |
|---|---|
| 子代理要跑超过几分钟 | **用** |
| 产出是报告／调研／审计／清单这类长文本 | **用** |
| 同时并行多个子代理 | **用** |
| 网络或会话不稳定 | **用** |
| 一次几十秒的小问题 | 不必 |

## 与驱动内两项保护的关系

三者互补，不重复：

| 机制 | 覆盖什么 | 局限 |
|---|---|---|
| `waitForBackgroundTasks` | 正常结束的一轮：持有本步直到后台工作跑完 | abort／硬杀无效 |
| `harvestOrphanedSubagents` | 已经死掉之后：从 transcript 捞回过程产出 | 捞不回从未生成的内容 |
| **本模板** | **从一开始就不把交付物押在回复上** | 需要在 prompt 里明确要求 |

前两项是**事后补救**，本模板是**事前免疫**——所以它才是这三者里最该先做的一项。
